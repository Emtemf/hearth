# G4C+E：从需求到可验证执行

G4C+E 是任务规格、计划和执行的质量框架，但不是要求一条原始需求在创建瞬间填满六个字段。
Hearth 把「用户说了什么」「确认后的需求」「选择了什么计划」「实际执行了什么」「证据证明了什么」
分成不同的、可版本化的对象，禁止用一张可变 Task 表承载全部生命周期。

```text
TaskRequest                 原始需求；允许含糊，保留外部来源和原文
    ↓ clarify / gather context
TaskSpecVersion             不可变需求版本：Goal、Context、验收标准、约束、Evidence policy
    ↓ plan
PlanVersion                 不可变计划版本：Choice、子任务、Checkpoint、Correction
    ↓ execute
TaskExecution（表名 task）  运行生命周期；固定引用一个 spec version 和 plan version
    ↓ verify
EvidenceClaim + VerificationRecord
```

用户改变目标或约束时创建新的 `TaskSpecVersion`；重新规划时创建新的 `PlanVersion`。已经开始的执行不得
偷偷切换版本：取消/暂停旧执行后显式创建新执行，历史仍能回答「哪次执行使用了哪个需求和计划」。

---

## 阶段性 invariant

| 阶段 | 进入条件 | 允许产生的 G4C+E 内容 | 退出条件 |
|---|---|---|---|
| `INTAKE` | `TaskRequest` 已持久化 | 初始 Goal、已知 Context、gaps | 请求可处理或转 `CLARIFYING` |
| `CLARIFYING` | Goal/Context 尚不足 | 人工澄清、代码/文档探测、假设与验证办法 | 新 `TaskSpecVersion` 满足 spec invariant |
| `PLANNING` | 已选择 spec version | Choice、subtasks、Checkpoints、Correction | 新 `PlanVersion` 满足 plan invariant |
| `READY` | spec/plan 均已冻结 | 预算、Profile、workspace 等运行参数 | 获得执行许可 |
| `RUNNING` | 创建 `TaskExecution` | Execution Claim 与 Artifact | 进入 checkpoint 或终局验证 |
| `VERIFYING` | 有待验证 claim | VerificationRecord | Goal claims 全部 PASSED，或按 Correction 处置 |
| `AWAITING_HUMAN` | 需要决策/批准 | 人工 VerificationRecord 或新 spec/plan | 版本 CAS 批准、改规或取消 |
| 终态 | 已完成状态转换 | 审计记录 | `SUCCEEDED` 必须引用通过的 Goal Verification |

具体约束：

- `TaskRequest` 只要求原始 `brief` 和来源，不要求可验证 Goal。
- `TaskSpecVersion` 发布时必须有可验证 Goal、Context gaps 处置、验收标准、约束和 Evidence policy。
- `PlanVersion` 发布时必须有 Choice、Checkpoint、Correction；纯人工直办任务可使用显式的 `NO_PLAN`
  计划版本，不能靠 `NULL` 偷渡。
- `TaskExecution` 只保存运行状态、版本引用、预算、取消 fencing、父子关系和时间，不复制可变 G4C+E JSON。
- `gaps` 非空且没有明确的 `assume_and_verify` / `escalate_to_human` 处置时，禁止进入 `READY`。

`CLARIFYING` 是一等状态，不是 planner prompt 里的隐式动作。澄清可以由人、受限的 context-gathering
Session 或 deterministic tool 完成；每次输入都保留来源。

## G4C+E 分布在哪些对象

```text
Goal          TaskSpecVersion.goal + acceptanceCriteria
Context       TaskSpecVersion.contextItems + contextGaps
Choice        PlanVersion.decision + alternatives + tradeOffs
Checkpoint    PlanVersion.checkpoints
Correction    PlanVersion.correctionPolicy
Evidence      EvidenceClaim + VerificationRecord + Artifact
```

E 不是「每个字段都硬贴一个 Artifact ID」，而是为不同认识论类型规定不同的可追溯方式。

### Context / reasoning 类型

| 类型 | 含义 | 来源要求 | 验证要求 |
|---|---|---|---|
| `FACT` | 可观察事实或 premise | 必须有 `SourceRef` | 来源可变时在执行前重验 |
| `HUMAN_REQUIREMENT` | 人的需求、偏好、政策 | 必须有 `human_stated:{auditEventId}` | 不伪造外部证明 |
| `INFERENCE` | 从 premises 推出的判断 | 引用 premise IDs | 保存 reasoning；不强求伪外部 citation |
| `HYPOTHESIS` | 暂未证实的假设 | 可无外部 source | 必须记录 uncertainty 和 verification plan |
| `DECISION` | 对 trade-off 的选择 | 引用 premise/inference/hypothesis IDs | 记录 alternatives 与代价 |
| `EXECUTION_CLAIM` | 关于产出、Checkpoint 或 Goal 的断言 | 必须建 `EvidenceClaim` | 必须有 PASSED `VerificationRecord` 才成立 |

示例：

```json
{
  "id": "ctx-1",
  "kind": "FACT",
  "statement": "项目使用 Spring MVC",
  "sourceRefs": ["file:AGENTS.md:58"]
}
{
  "id": "ctx-2",
  "kind": "INFERENCE",
  "statement": "同步 servlet 更符合当前可调试性目标",
  "premiseIds": ["ctx-1", "ctx-human-1"]
}
{
  "id": "ctx-3",
  "kind": "HYPOTHESIS",
  "statement": "32 MiB request limit 足够覆盖 Claude Code 请求",
  "uncertainty": "MEDIUM",
  "verificationPlan": "运行真实请求 corpus contract test"
}
```

## Artifact、Claim 与 Verification

Artifact 是不可变、可寻址的材料，不自动证明任何结论。一个 `test-output` Artifact 只说明某段输出存在，
不能单独证明「当前代码的测试通过」。证明关系至少包含：

```text
EvidenceClaim
  subjectType / subjectId       被证明的 Task、Checkpoint、Artifact 或 Operation
  claimType / statement         具体断言
  sourceStateRef                断言对应的源状态

VerificationRecord
  claimId
  artifactIds                   支撑材料，可为多个
  verifierKind / verifierRef
  method
  sourceStateRef                验证时再次绑定源状态
  status / verifiedAt
```

`sourceStateRef` 对代码任务至少包含可取得的：

- Git commit/tree SHA；dirty workspace 使用 base SHA + normalized diff SHA。
- `workspaceRootId + relativeCwd`，禁止仅存任意绝对路径。
- 命令、工具及版本、环境/fixture 标识。

若当前 source state 与 VerificationRecord 不一致，记录转为 `STALE`，不能继续证明当前执行。

`verifierKind`：

- `DETERMINISTIC_TOOL`：exit code、schema validation、hash、HTTP contract 等可机械判断的规则。
- `REVIEWER_AGENT`：架构合理性、代码质量、文字内容等需要模型判断的检查；必须使用独立 reviewer Session，
  保存 Review Artifact，原 agent 不得自证。
- `HUMAN`：产品判断、风险接受或无法自动化的验收。
- `COMPOSITE`：组合多个已通过的 VerificationRecord；组合器只执行显式逻辑，不暗中调用模型。

标准流程：

```text
original Session → Artifact + EvidenceClaim
    ├─ deterministic rule → VerificationRecord
    ├─ reviewer Session → Review Artifact → VerificationRecord
    └─ human decision → VerificationRecord
```

Orchestrator 可以执行 deterministic verifier 和状态组合，但不使用 Spring AI ChatClient 自己评审语义内容。

## TaskSpecVersion 与 PlanVersion

```text
TaskSpecVersion {
  requestId
  version
  goal
  contextItems[]          // 带 kind、SourceRef/premiseIds
  contextGaps[]           // 每项带 resolution strategy
  acceptanceCriteria[]
  constraints[]
  evidencePolicy
  createdBy
}

PlanVersion {
  specVersionId
  version
  decision               // 引用 premises，不伪造 citation
  alternatives[]
  tradeOffs[]
  subtaskTemplates[]      // 每项会创建 Child TaskRequest/TaskExecution
  checkpoints[]           // claim 模板、verifier kind、method
  correctionPolicy
  createdBySessionId
}
```

Plan 的 alternatives 是决策分析，不要求每句判断都有外部来源；事实 premise 必须有来源，推论必须引用
premise，假设必须有验证计划。planner 输出在发布前由 application service 做结构校验。

## Task Tree、Session Graph 与 Internal Dispatch

- `request` 是业务委托：创建 `ChildTaskRequest`，形成 Child `TaskExecution` 后再创建或选择执行 Session。
  Child Task 有独立 spec、plan、Goal、Checkpoint 和从父预算划拨的额度。
- `consult` 是受限咨询：不创建 Child Task，只在目标 Session 创建 Invocation；不可继续派生。
- `notify` 是单向事件：不创建 Task；是否产生 Invocation 取决于目标 adapter 是否需激活。
- `escalate` 作用于当前 Task：必须引用至少一个 `EvidenceClaim` 或失败 VerificationRecord，并进入 Inbox。

因此：

```text
Task Tree       业务分解、预算、Checkpoint、级联取消
Session Graph   agent 身份与协作关系
Invocation      一次具体激活
Dispatch        连接这些对象的领域命令/事件
```

`request` 不得用「同一 Task 下多建一个 Session」绕过 Child Task 的 Goal、预算和取消语义。完整协议见
`docs/05-a2a-and-loops.md`。

## Correction 与完成规则

- Checkpoint 失败执行 `retry` / `try_alternative` / `escalate_to_human`，每次 attempt 都新增 VerificationRecord。
- `escalate` 必须带 claim/verification 引用；只有 Artifact ID 而没有具体 claim 的请求不处理。
- `SUCCEEDED` 要求当前 spec version 的全部 Goal claims 都有非 STALE 的 PASSED VerificationRecord。
- 失败、阻塞与「无法实现」同样是 Execution Claim，必须有可核验记录，不能只凭 agent 文字。
- Artifact 遭 `SECURITY_PURGE` 后，引用它的 VerificationRecord 转 `INVALIDATED`，相关 claim 重新进入待验证。

Artifact 模块只负责存储和寻址；Evidence 语义、verifier 调度与 Goal 是否通过由任务编排模块负责。
