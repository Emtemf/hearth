# G4C+E：任务设计方法论

G4C+E 是平台所有任务的设计标准，也是评审 planner 输出质量的框架。
五个要素缺一个，这个任务就是一个潜在的失控点。

```
Goal        我要达成什么？什么叫成功？          → 缺失导致目标漂移
Context     当前知道什么？还缺什么？            → 缺失导致凭空计划、幻觉
Choice      为什么这么走？还有哪些路径？        → 缺失导致机械执行，无法复盘
Checkpoint  怎么知道当前步骤对不对？            → 缺失导致发现问题时只能重来
Correction  发现偏差后怎么办？                  → 缺失导致无法恢复
──────────────────────────────────────────────────────
Evidence    每一步的断言从哪来？                → 缺失导致以上五条全部可被伪造
```

**E 不是第六个独立要素，而是贯穿其余五条的约束**：
G、C、C、C、C 告诉你要做什么，E 要求每一步都必须拿出可独立核验的证据。
没有 E，agent 可以在每一步自报正确，整个框架退化成走形式。

---

## Evidence 的核心规则

> **任何断言必须附带可独立核验的 Artifact。没有 Artifact，断言不成立。**

| 断言类型 | 允许的 Evidence | 不允许 |
|---|---|---|
| "测试通过" | 测试运行的完整 stdout + 退出码（Artifact） | agent 文字描述 |
| "实现完成" | 代码 diff（Artifact） | "我已经写好了" |
| "这个项目用 React" | package.json 路径 + 相关行 | 记忆里说的 |
| "之前踩过这个坑" | 记忆卡片 ID（有 sourceSessionId 可追溯） | 凭空声称 |
| "Goal 无法实现" | 具体的工具调用结果 / 错误输出（Artifact） | 推断或预感 |
| "选这个方案因为 X" | 至少引用一条 Context 来源或已有 Artifact | "我认为" + 空气 |

## E 在各要素上的具体体现

### Goal + E
成功标准必须是**可用工具验证的**，不能只靠 agent 自报：
- 好：`POST /auth/login 返回 200，单测覆盖率 > 80%` → 可以跑命令检查
- 坏：`功能正常` → 谁来判断"正常"？

### Context + E
`context.known` 里的每一条必须标注来源：
```
{ "fact": "项目使用 PostgreSQL 16", "source": "file:pom.xml:line:42" }
{ "fact": "上次类似任务用了 Repository 模式", "source": "memory:card-abc123" }
```
来源类型：`file:{path}:{line}` / `memory:{cardId}` / `artifact:{id}` / `human_stated`
没有来源的 known 条目视为未经验证的假设，必须标记为 `gaps`。

### Choice + E
`choiceRationale.chosen` 必须引用至少一条 Context 来源：
- 好：`选 Repository 模式，因为 memory:card-abc123 记录了这个项目偏好此模式`
- 坏：`Repository 模式更好` → 凭什么？

### Checkpoint + E
**编排层不接受 agent 的文字结论，只接受 Artifact ID，自己验证。**

流程：
```
agent 完成子任务
    → 必须提交 Artifact（代码 diff / 测试报告 stdout / 文档文件）
    → 编排层拿到 Artifact ID，独立执行验证逻辑
    → 验证通过 → 继续
    → 验证不通过 → 按 correction 策略处置，不相信 agent 说"我觉得应该对"
```

agent 只提交 Artifact ID，不提交结论。结论由编排层自己得出。

### Correction + E
`escalate` 消息必须附带触发证据的 Artifact ID：
- 好：`Goal 无法实现，证据：artifact:test-run-xyz（stderr 包含'表不存在'），artifact:schema-diff-abc（schema 与代码假设不符）`
- 坏：`我觉得这个 Goal 做不到` → 不处理，要求补充证据

## Task Schema 的完整 G4C+E 映射

```
Task {
  brief       任务的自然语言描述（人类读的）

  goal        成功标准，可用工具验证的判据
              例："POST /auth/login 返回 200，
                   mvn test 退出码为 0，
                   grep -r 'plaintext_password' src/ 无输出"

  context {
    known [
      { fact: string, source: "file:{path}" | "memory:{id}" | "artifact:{id}" | "human_stated" }
    ]
    gaps  [需要先收集的信息]  // gaps 非空时先跑 context-gathering，不直接开始实现
  }

  checkpoints [
    {
      after:    "步骤描述"
      verify:   "验证命令或 Artifact 检查规则"
      evidence: "期望的 Artifact 类型"  // agent 必须提交这类 Artifact 才算完成
    }
  ]

  correction {
    onCheckpointFail  "retry" | "escalate_to_human" | "try_alternative"
    onGoalBlocked     "escalate_to_human"  // 必须附带 Evidence Artifact
  }
}
```

## Planner 输出的 G4C+E 结构

```
PlanArtifact {
  goal              继承自 Task.goal（planner 确认理解了目标）
  contextGaps       发现的信息缺口 + 处理方式 + 来源标注
  subTasks [
    {
      goal          子任务自己的完成标准
      assignTo      Profile
      dependsOn     前置子任务 ID
      checkpoint {
        verify      验证命令
        artifactRequired  必须提交的 Artifact 类型
      }
    }
  ]
  choiceRationale {
    chosen        选择理由（必须引用至少一条 Context 来源）
    alternatives  备选方案 + 放弃原因（每条也要有来源支撑，不能纯靠判断）
    risks         当前方案的已知风险点（标注是假设还是有证据）
  }
}
```

## A2A 消息类型（含 escalate）

```
request    任务委托（可再派生）
consult    询问（不可再派生，直接回答）
notify     单向通知
escalate   agent 主动上报「Goal 无法实现」
           → 必须附带 evidenceArtifactIds（空数组不接受）
           → 必须进 Inbox，不能被自动处理
           → 必须包含建议的备选方案（至少一个）
```

---

## Checkpoint：进度验证不等于约束检查

约束检查回答“这个操作是否允许”，Checkpoint 回答“当前产出是否达到可验证标准”。
前者防止违规，后者防止方向正确性漂移；两者都必须独立执行。
自动验证不了的 Evidence 进入 Inbox，由人核验，不能由原 agent 自证。

## G4C+E 用于 Hearth 自身设计评审

| 要素 | 对应设计文档 | Evidence 要求 |
|---|---|---|
| Goal | 07-roadmap.md 里程碑验收标准 | 验收标准必须可执行（命令 / 截图 / 测试） |
| Context | 08-operations.md 部署拓扑 | 来自实际环境探测（`java -version`、转录文件检查） |
| Choice | 00-stack-decision.md ADR | 每个决定引用了具体的对比数据 |
| Checkpoint | 每个里程碑的具体验收 | 有可执行的验证步骤，不是主观判断 |
| Correction | escalate 机制 | 必须附带 Artifact，不接受纯文字上报 |
| Evidence | 贯穿所有 | Artifact 存储模块是 E 的物质基础 |

**Artifact 存储模块（02-modules.md）是 Evidence 能落地的前提**——
没有可寻址、可独立核验的 Artifact，E 只是原则，无法执行。
